# 评审与排错

## 一、四类常见失败

Denied Topics 拦多或拦少，原因通常是以下四种写法之一【博客】：

| 失败 | 表现 | 原因 |
|---|---|---|
| 误拦正常请求 | 同领域的正常问题被拦 | 主题按领域（Finance、Legal、Compensation）而不是用户意图设计 |
| 漏拦目标请求 | 换个说法就过 | 定义是关键词清单，换了词就漏，带同样词的无关请求反而被拦 |
| 示例教错 | 只拦住一种问法；提到某个实体的请求被误拦 | 5 条示例是同一个意思的改写；示例中出现了国家、产品、公司名 |
| 主题互相干扰 | 命中主题不稳定；组合起来误拦 | 定义重叠，争抢同一输入 |

## 二、反模式

即使定义的其他部分写得很好，以下写法也会导致主题拦错【博客】：

| 反模式 | 错误写法 | 改正方向 | 详见 |
|---|---|---|---|
| 定义写成指令 | "Block all content related to…" | 描述主题是什么 | writing-topics.md 第 3 节 |
| 主要靠排除来界定 | "All content except…" | 正面描述主题范围 | 第 3 节 |
| 列触发词 | "Questions containing words like…" | 描述概念本身 | 第 1、3 节 |
| 用主题拦特定词或实体 | 竞品名、人名主题 | Word filter 或 Sensitive information filter | policy-selection.md |
| 示例中出现具名实体 | 示例里写国家、产品、竞品、公司名 | 用泛称 | writing-topics.md 第 4 节 |
| 示例只是改写定义 | 5 条同义问句 | 换成覆盖不同子情形的边界示例 | 第 4 节 |
| 定义含糊，靠示例撑 | 一句宽泛定义加 5 条示例 | 先把定义写具体 | 第 3、4 节 |

## 三、评审检查清单

评审客户已有的配置时，逐项检查。

### Guardrail 级别

- [ ] tier 和流量语言匹配。Classic 的 Denied Topics 只支持英语、法语、西班牙语【文档】
- [ ] 使用 Standard tier 时配置了跨区域 profile，并确认符合数据驻留要求【文档】
- [ ] 被拦提示语给了用户出路（换个问法、转人工）
- [ ] 应用引用的是发布过的版本号，而不是 DRAFT
- [ ] 使用 InvokeModel 时用输入标签包住了用户输入，否则 Prompt attack 不生效【文档】

### 策略分流

- [ ] 没有用主题处理通用安全类别、越狱、固定词表、个人信息【博客】
- [ ] 没有用"除业务范围外都拦"的主题做范围控制【文档】
- [ ] Word filter 词条考虑了单复数等变体，因为它是整词匹配【文档】
- [ ] 中文词条的 Word filter 经过实测，因为文档只列出英语、法语、西班牙语【文档】

### 每个主题

- [ ] 名称是具体行为短语，不是领域词或机构标签
- [ ] 名称没有重复正常教育类问题会用的歧义词
- [ ] 名称只含英文字母、数字、空格和 `- _ ! ? .`，不超过 100 字符【文档】
- [ ] 定义以动作或内容类型开头，有具体对象和限定条件
- [ ] 定义没有指令、否定式主体、关键词清单、实体捕获、示例句
- [ ] 定义长度在当前 tier 限制内（Classic 200，Standard 1,000）【文档】
- [ ] 5 条示例覆盖不同子情形和句式，至少一条靠近边界【博客】
- [ ] 示例中没有国家、产品、竞品、公司名，除非主题针对该实体【博客】
- [ ] 尾部排除只用于类别明显不同的情况【博客】
- [ ] 输入、输出的启用和动作是有意设置的

### 主题集

- [ ] 没有两个主题共用主要动作和对象；有的话已合并或加了区分特征【博客】
- [ ] 没有"宽主题兜底窄主题"的组合【博客】
- [ ] 相似主题不相邻【博客】
- [ ] 主题数量合理，相关主题较多时考虑分到多个 guardrail【博客】

### 测试

- [ ] 有评测集，包含明确应拦、明确应放行、靠近边界三类
- [ ] 每条用例重复测试至少 3 次
- [ ] 最近一次改动后重跑了全部评测集
- [ ] 记录了每条被拦用例的命中主题

## 四、症状排查

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 同领域的正常问题被拦 | 名称或定义是领域式的 | 改成动作式名称和定义 |
| 教育类问题被拦（"什么是 X"） | 名称重复了歧义词；缺少目的限定 | 改名；加"for the user's own…"之类的目的锚定 |
| 报告类请求被拦（"我要报告 X"），主题本意是拦"让助手处理 X" | 报告和处理用词重合，尾部排除不可靠 | 双条件锚定；把区分点放进名称；上游意图路由，在 Guardrails 之前把报告类请求交给人工 |
| 数据查询被拦（"给我看我的 X"） | 主题对象和查询对象相同 | 在定义中明确动作是"建议、判断"而不是"查看"；重新测试 |
| 换个说法就漏 | 示例都是改写；定义是关键词清单 | 换成覆盖不同子情形和句式的边界示例；描述概念 |
| 提到某个国家、公司的请求被拦 | 示例或锚定里有该实体 | 从示例中删除实体；锚定到类别 |
| 同一输入有时拦有时不拦 | 输入处于主题边缘 | 收紧定义、加锚定、补边界示例；产品上让错误拦截可恢复 |
| 命中的主题不对，或在两个主题间跳 | 两个主题重叠；相似主题相邻 | 合并；加区分特征；调整顺序 |
| 新增主题后，旧用例结果变了 | 主题集整体评估 | 新需求优先扩充已有主题示例；合并重叠；重跑全部评测 |
| 只改了顺序，结果就变了 | 顺序影响评估结果【文档】 | 固定顺序；相似主题隔开；每次调整都重测 |
| 中文请求漏拦或误拦 | 使用了 Classic tier；定义和示例语言与流量不符 | 用 Standard tier；对比英文与中文示例的效果 |
| 越狱、暴力内容漏拦 | 用主题处理了原生策略的类别 | 改用 Prompt attack、Content filter |
| 竞品名有时拦有时不拦 | 用主题做精确词匹配 | 改用 Word filter |
| 用户提到竞品就被拦 | Word filter 对输入也启用了 | 需求只针对回答时，只对输出启用 |

## 五、修误拦的顺序

从改动最小、最可靠的方法开始。每一步改完都重跑全部评测集，确认没有引入新的问题。

1. 检查是否该交给其他策略。
2. 把领域式名称改成动作式。
3. 把定义改成动作开头，加具体对象和限定条件。
4. 替换示例：去掉改写和具名实体，换成边界示例。
5. 加目的或情境锚定。
6. 被误拦的请求和主题类别明显不同时，加简短尾部排除。
7. 措辞几乎一样时，用双条件锚定，或把区分点放进名称。
8. 检查相邻主题：合并重叠，隔开相似主题。
9. 仍然无法区分时，用上游意图路由，或者接受残留风险，并让错误拦截可恢复。

第 1 到 7 步来自博客的建议，第 8 到 9 步来自博客的主题集管理和局限性部分。这个先后顺序是本 skill 的建议。
